# 2026.9.16

_Released 2026-10-01 · [compare 2026.9.14…2026.9.16](https://github.com/perosb/qvantum_custom_component/compare/2026.9.14...2026.9.16) · [all releases](https://github.com/perosb/qvantum_custom_component/tree/main/docs/releases)_

A reliability-focused release. The cloud transport is hardened end to end — a real
reauth flow, one error contract across reads and writes, serialized token refresh
and proper 429 handling — while a batch of Modbus-only diagnostics lands (alarm
sensors, display firmware, a heating-curve advisor and a ventilation-filter
calendar). Config-entry diagnostics, DHW device triggers and wider DHW start/stop
limits round it out.

> [!IMPORTANT]
> Setup is **Cloud HTTP** or **local Modbus**.
> Local Modbus is read-only until writing is enabled.
> SmartControl stay cloud-only.


> [!WARNING]
> **Modbus mode**
> Enabling Modbus writing means you accept full responsibility for values written to the pump.
> Incorrect or out-of-range values may void the warranty and/or affect lifecycle and performance.


> [!WARNING]
> **Cloud mode**
> Elevate access assigns "Remote Service" (service tech) rights to your user. Cloud HTTP only.
> Cloud mode uses the same internal API as the app. Use at your own risk ;)

## New features

### Add Modbus alarm sensors and problem binary ([#233](https://github.com/perosb/qvantum_custom_component/pull/233))

Map Modbus input registers 150–155 (`active_alarms`, `alarm_1_code`–`alarm_5_code`) and poll them on the existing 150–170 island so QGM1/QGM2 inputs 119–146 stay unread. Expose the six values as Modbus-only diagnostic sensors (integer display; count is a measurement). Derive `alarm_active` as a PROBLEM binary sensor (main UI, not diagnostic) plus device trigger/condition and translations in all locales.

### Widen DHW start/stop limits and keep start below stop ([#234](https://github.com/perosb/qvantum_custom_component/pull/234))

Widen `tap_water_start` / `tap_water_stop` (DHW Normal, holdings 56/57) from 50–65 / 60–80 °C to **50–80 °C** on both number entities and the water heater target. Keep start below stop: the start slider max is `stop - 1`, the stop slider (and water heater min) is `start + 1`. Writes that would invert the pair raise `HomeAssistantError`. Applies in cloud HTTP and local Modbus; both transports already share these settings.

### Add cloud reauth flow ([#238](https://github.com/perosb/qvantum_custom_component/pull/238))

Cloud `AuthError` now raises `ConfigEntryAuthFailed` from the main and maintenance coordinators, so Home Assistant starts a reauth flow instead of polling a dead session. Modbus mode keeps the existing local fallback (`UpdateFailed` / cloud-unavailable result) and never triggers reauth. New `async_step_reauth` / `async_step_reauth_confirm` in the config flow: prefilled username, password re-validation via `validate_input`, in-place credential update (`data_updates`) and entry reload. `reauth_confirm` step + `reauth_successful` abort strings added to all 11 translations.

### Cache enabled metrics between registry changes ([#250](https://github.com/perosb/qvantum_custom_component/pull/250))

Cache `_get_enabled_metrics()` per device; recompute only after an `entity_registry_updated` / `device_registry_updated` event (registered via `config_entry.async_on_unload`, so they unload with the entry). Hoist the per-entity `allowed_metrics` set out of the loop — it was rebuilt identically for every registry entity. Cloud and Modbus transports share the same coordinator path; no wire behavior change. Depends on #249.

### Add Modbus display firmware version sensor ([#255](https://github.com/perosb/qvantum_custom_component/pull/255))

Adds a **Display firmware version** diagnostic sensor for Modbus mode, sourced from the identity island input registers 191-193 (already used by the setup/probe path). The coordinator re-probes the identity island at most once per hour (`MODBUS_SW_VERSION_REFRESH_INTERVAL = 3600`, first poll after start refreshes immediately). On a change it updates the cached device, the persistent store, and the HA **device registry**, so a new display firmware shows up without a restart. A refused identity read is logged and never fails the poll. The sensor is Modbus-only (`QvantumDisplayFirmwareEntity`) and shares the cloud firmware sensor's unique id and translation key (`firmware_display_fw_version`), so the entity survives a cloud ↔ Modbus reconfigure. No translation changes needed — the key already exists in all 12 languages. Cleanup keeps `display_fw_version` in Modbus mode so the entity is not removed after creation. Transport: Modbus only; cloud firmware/access monitoring is unchanged. Related: #254 fixes the cloud-side device registry sync; this PR is independent.

### Add redacted config-entry diagnostics ([#259](https://github.com/perosb/qvantum_custom_component/pull/259))

Add `custom_components/qvantum/diagnostics.py` with `async_get_config_entry_diagnostics`, exposing transport mode (Modbus/cloud), poll interval, device id, the latest coordinator `values`, the enabled-metrics cache, DHW EMA parameters and extra-DHW `restore_at`. Firmware/access data from the maintenance coordinator is included, but `access_level` is reduced to numeric fields only — the `expiresAt` timestamp is dropped entirely. Credentials/tokens (password, username, token, refresh_token, …) are redacted with `async_redact_data`; an entry whose `runtime_data` is missing still renders without crashing. Entity registry counts (total/enabled) are reported best-effort. No protocol or entity behavior changes.

### Add DHW shower, tank-low and extra-DHW triggers ([#262](https://github.com/perosb/qvantum_custom_component/pull/262))

New device triggers/conditions on the Qvantum device: `ALL_STATUS_METRICS` now covers `sensor` (`bf1_l_min`, `tap_water_cap`) and `switch` (`extra_tap_water`) status entities. The filter-soon-due numeric trigger moved into shared `NUMERIC_TRIGGER_MAP` / `NUMERIC_CONDITION_MAP` tables; behavior unchanged. Prefix-collision keys `extra_tap_water_60min` (button) and `tap_water_capacity_target` (number) are registered as known non-status keys so longest-prefix unique-id matching stays exact. Translations (`trigger_type` + `condition_type`) added in all 11 locales. No transport-visible behavior change beyond the new automations.

- `dhw_shower_started` / `is_dhw_shower_active` — numeric state on `bf1_l_min` above `DHW_MIN_SHOWER_FLOW_LPM` (3.0 L/min). Strings say "tap water" because flow also rises for dishwashers/washing machines.
- `dhw_tank_low` / `is_dhw_tank_low` — numeric state on `tap_water_cap` below new `DHW_TANK_LOW_SHOWERS` (2.0). Modbus-only; listed only when the entity exists in the registry.
- `extra_dhw_finished` / `is_extra_dhw_active` — state trigger `to: "off"` / condition `on` on the `extra_tap_water` switch, in both transports.

### Add heating curve advisor sensor ([#263](https://github.com/perosb/qvantum_custom_component/pull/263))

Adds a **Modbus-only** derived sensor `heating_curve_advisor` (no cloud equivalent, gated like the display firmware sensor). The coordinator samples `room - indoor_temperature_target` (BT2, or the external room sensor when that source is selected) **only while `hp_status` is Heating**, over a rolling 6 h window. Once the window is full: `reduce` when the mean deviation is > +1.0 °C, `increase` when < −1.0 °C, otherwise `ok`. Attributes: `mean_deviation_c`, `observed_hours`, `window_hours`, plus `curve_type_heating` and `bt1` for context. Advice only — nothing is written automatically. The window is in-memory and refills after a restart. Adds `hp_status`/`bt1` to `REQUIRED_MODBUS_METRICS` (BT2 is already in `REQUIRED_METRICS`; `indoor_temperature_target` comes from the always-read holding registers), lists the metric in `DEFAULT_ENABLED_MODBUS_ONLY_METRICS`, adds `mdi:tune-variant` and translations (name + `reduce`/`ok`/`increase` states) in all 11 locales. Documents the semantics in `docs/heating-curve.md`.

### Add read-only ventilation filter calendar ([#264](https://github.com/perosb/qvantum_custom_component/pull/264))

Add a read-only `calendar` platform for the ventilation filter, Modbus only. The pump reports `ventilation_filter_time_left` (input 91, hours) but no absolute replacement date, and the cloud API has no equivalent metric. The due time is anchored from the first observed reading and persisted per entry in `qvantum.filter_calendar.<entry_id>`, so a restart does not move the event. A jump up in remaining hours (new filter fitted) re-anchors it, and a stale anchor is realigned with the live reading. One **all-day** `CalendarEvent` on the local due date; `async_get_events` returns it only when the requested range overlaps that day. The entity is not created in cloud mode, and switching modes prunes it from the entity registry. `ventilation_filter_time_left` sits in `REQUIRED_MODBUS_METRICS`, so disabling the diagnostic sensor does not blank the always-created calendar. Entity name added to all 11 locales as `entity.calendar.ventilation_filter_due`.

## Bug fixes

### Enforce translation key parity and fill gaps ([#236](https://github.com/perosb/qvantum_custom_component/pull/236))

Add `test_translation_key_structure_matches_english`, comparing every locale's full key-path structure against `en.json` and failing on missing or unexpected keys. Add the missing `entity.water_heater.dhw` block to `cs`, `da`, `de`, `es`, `fi`, `fr`, `hu`, `nl`, and `pl`, using existing locale terminology for the name and `eco`/`normal`/`extra`/`smart`/`off` states. Rename `es` `entity.sensor.extra_tap_water_stop` to the actual code key `tap_stop` (text unchanged). Remove the stale `sv` `entity.switch.use_adaptive`; `use_adaptive` is a select entity and the correct select entry already exists. No production code changed; translations and tests only.

### Return a valid climate feature flag and report cooling ([#239](https://github.com/perosb/qvantum_custom_component/pull/239))

`supported_features` returned `{}` when no indoor sensor is in use. HA's climate service does bitwise checks (`supported_features & ClimateEntityFeature.TARGET_TEMPERATURE`), so `climate.set_temperature` raised `TypeError`. It now returns `ClimateEntityFeature(0)`. `hvac_action` now maps `hp_status == 4` to `HVACAction.COOLING` (previously fell through to idle). Hot water (`hp_status == 2`) intentionally stays `IDLE` since it does not heat the room. Uses the `HP_STATUS_*` constants from `const.py` instead of magic numbers.

### Use native_value for sensor and number state overrides ([#240](https://github.com/perosb/qvantum_custom_component/pull/240))

`SensorEntity.state` and `NumberEntity.state` are `@final` in Home Assistant and delegate to `native_value` (unit conversion, display precision). The seven overrides in `sensor.py` / `number.py` shadowed that final property, so e.g. °F conversion never applied. Renamed all overrides to `native_value`, the documented extension point. Tests updated to assert `native_value`, which also fails if someone reintroduces a `state` override (the mocked base classes have no `state`).

### Accept string device ids in extra_hot_water service ([#241](https://github.com/perosb/qvantum_custom_component/pull/241))

`extra_hot_water` required `device_id: int`, but Modbus device ids are serial strings, so the service rejected every local-mode call. It now accepts an int or a non-empty string and normalizes to `str` (matching the client type hints and `services.yaml`). Normalization never round-trips through `int`, so leading zeros in serials are preserved. Empty, boolean, and null ids are rejected with a validation error.

### Avoid duplicate cloud sign-ins on auth failure ([#243](https://github.com/perosb/qvantum_custom_component/pull/243))

`_ensure_valid_token` caught `AuthError` raised by `authenticate()` and then called `authenticate()` again, so a rejected password produced two to three Firebase sign-in attempts per poll (rate-limit risk). It now refreshes once, signs in at most once, and lets `AuthError` propagate. A token with no expiry is now treated as invalid instead of comparing a datetime against `None`. Client-only change; no Home Assistant imports touched.

### Handle cloud rate limiting as a warning in the coordinator ([#249](https://github.com/perosb/qvantum_custom_component/pull/249))

Add a dedicated `APIRateLimitError` branch in `QvantumDataUpdateCoordinator.async_update_data`. Cloud HTTP 429s now log a WARNING (no traceback) and raise `UpdateFailed("Rate limit exceeded: ...")` instead of falling through to the generic unexpected-error path. Cloud transport only; no Modbus behavior change. Stacked work: this is the base of the P2 stack. The next PR (metrics caching) depends on it.

### Unify cloud error handling across reads and writes ([#251](https://github.com/perosb/qvantum_custom_component/pull/251))

`_handle_response`: 401/403 clear the stored token and raise `AuthError`, 429 raises `RateLimitError`, everything else `TransportError` — one error contract for the client. Writes (`_send_command`, `_update_settings` via `_request_json`) now validate the HTTP status by default, so a failed update raises instead of returning an error body as if it were a result. Reads keep their ETag/304 semantics and now raise 429 explicitly instead of silently serving stale data (or wiping cached metadata). A throttled token refresh propagates `RateLimitError` instead of falling through to a full sign-in. Maintenance coordinator: 429 → warning + `UpdateFailed` without a traceback; config flow maps 429 to `CannotConnect`. Cloud-only changes; Modbus transport untouched. 429s from these paths are handled by the warning branch from #249. Depends on #250. Stack: #249 → #250 → this.

### Sync device registry firmware versions from fresh data ([#254](https://github.com/perosb/qvantum_custom_component/pull/254))

The maintenance coordinator read firmware versions out of `self.data` when updating the device registry, but `self.data` still holds the *previous* poll at that point (the coordinator assigns the update result after the method returns). A detected firmware update therefore wrote the **old** versions, and a version seen for the first time after a restart was never written at all — the new `sw_version` only showed up after an integration reload. Pass the versions just fetched into `_update_device_registry_firmware_versions` and run the sync on **every** successful check (cloud mode), not only when a change was detected. Skip the registry write when the stored `sw_version` already matches, so steady-state checks stay idempotent. `_create_firmware_update_notifications` no longer updates the registry; the sync is owned by the check method. User-visible: an updated display/CC/inverter firmware now appears on the Qvantum device page in Home Assistant within the next maintenance poll (≤2 h) instead of requiring a restart or integration reload. Transport: cloud only (the maintenance coordinator is cloud-only).

### Use SensorDeviceClass.TIMESTAMP for the tap_stop timer ([#256](https://github.com/perosb/qvantum_custom_component/pull/256))

The `tap_stop` timer sensor assigned the raw string `"timestamp"` as its device class while every other timestamp sensor uses `SensorDeviceClass.TIMESTAMP`. No user-visible behavior change today; the raw string silently diverges if Home Assistant ever changes the enum value. Extended the existing tap_stop setup test to assert the device class.

### Deduplicate missing-metric warnings ([#257](https://github.com/perosb/qvantum_custom_component/pull/257))

The cloud client logged a WARNING on every poll for each enabled metric the API does not return, flooding logs for users with disabled/enabled entity toggles. Keep a per-session `set` of already-warned metric names in `QvantumCloudClient`: warn once per metric, then log at debug level. `unauthenticate()` clears the set via `_reset_state()`, so a new session warns again (intended). Cloud-client only change; no HA imports.

### Redact device serial identifiers from diagnostics ([#265](https://github.com/perosb/qvantum_custom_component/pull/265))

Follow-up to #259: a real diagnostics dump showed the heat pump serial (identity) still present in several fields. Collect the entry `unique_id` and coordinator device identifiers (`device_id`, device `id`/`serial`, values `hpid`) and scrub every occurrence from **both mapping keys and string values** before redaction. Covered fields now become `**REDACTED**`: `entry.title` (`Qvantum QE-6 (3010…)` → `Qvantum QE-6 (**REDACTED**)`), `coordinator.device_id`, `device.id`, `device.serial`, `values.hpid` and the `enabled_metrics` cache key. `serial`, `device_id` and `hpid` were also added to `TO_REDACT` as defense-in-depth for value fields. For an unloaded entry the config-entry `unique_id` (the serial set by the config flow) still scrubs the title; no runtime data required.

### Classify cloud sign-in server errors as transport failures ([#267](https://github.com/perosb/qvantum_custom_component/pull/267))

`authenticate()` raised `AuthError` for every non-200, including 5xx, which sends Home Assistant into reauth for a transient Firebase outage. 5xx now raises `TransportError`; 429 stays `RateLimitError`; 400 surfaces Firebase `error.message` (e.g. `INVALID_PASSWORD`) in the `AuthError`. A 5xx from token refresh now raises `TransportError` instead of silently falling through to an extra full sign-in request. Cloud transport only; no user-visible behavior change on the Modbus path.

### Serialize cloud token refresh ([#268](https://github.com/perosb/qvantum_custom_component/pull/268))

`_ensure_valid_token()` had no synchronization: concurrent polls with an expired token each issued their own refresh/sign-in, multiplying requests and 429 risk. Added an `asyncio.Lock` with a double-check of the token after acquiring it, so waiters reuse the fresh token. A failed refresh/sign-in is cached for a 30 s cooldown and re-raised for subsequent callers, so a burst of concurrent callers with a rejected password only fires one Firebase request. Connection-level failures (`aiohttp.ClientError`, `asyncio.TimeoutError`) are wrapped in `TransportError` and cached too, and each caller gets a fresh exception instance. `unauthenticate()` clears the cache. Firebase returns its sign-in lockout (`TOO_MANY_ATTEMPTS_TRY_LATER`) as a 400, not a 429; it now maps to `RateLimitError`, which the coordinator treats as retryable, instead of `AuthError` (reauth). The lock lives in `__init__` (not `_reset_state`), so `unauthenticate()` resets only token state and the lock stays usable. Cloud transport only; Modbus already serialized reads/writes behind its own lock.

### Return APPLIED for tap-water no-op and validate capacity ([#270](https://github.com/perosb/qvantum_custom_component/pull/270))

Cloud `set_tap_water` returned `None` for a 0/0 call while Modbus returned `APPLIED`; both transports now report `{"status": "APPLIED"}`, so callers treat the result uniformly. The protocol docstring documents the no-op contract. Both clients now raise `ValueError` for tap-water capacities outside 1–7, so the same invalid call behaves the same per transport (HA numbers already clamp to 1–7; this guards direct client callers). Documented in `constants.py` that Modbus maps all levels through `TAP_WATER_CAPACITY_MAPPINGS` while cloud writes `tap_water_capacity_target` directly for levels 2–5. Cloud + Modbus transports; entity code unchanged (HA only writes tap-water temps >= 50 °C, so the no-op path is API-only).

### Guard cloud close and unify stale-cache handling ([#272](https://github.com/perosb/qvantum_custom_component/pull/272))

Track in-flight cloud HTTP requests so `close()` drains them before closing an owned session, mirroring the Modbus client's lock. Requests arriving after `close()` are rejected instead of touching a closing session. Unify stale-cache handling: on an unexpected HTTP status, `get_settings` now keeps the last known settings and logs a warning instead of clearing the cache, matching what `get_metrics` already did. Cloud transport only; no HA-facing API changes.
