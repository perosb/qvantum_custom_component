## New features

### Extract client package skeleton and protocol exceptions ([#207](https://github.com/perosb/qvantum_custom_component/pull/207))

Adds vendored `custom_components/qvantum/client/` as the seed of a standalone Qvantum communication library (HTTP + Modbus later). Moves protocol exceptions (`AuthError` / `ConnectionError` / `RateLimitError`) and protocol constants (DHW modes, fan presets, capacity map, relay power) into that package. Exceptions now store `status: int | None` instead of an `aiohttp` response object. `api.py` and `const.py` re-export the previous names so the rest of the integration is unchanged. This is PR 1 of the client-extraction plan. Follow-ups: move Modbus maps into `client.modbus`, then split `QvantumAPI` into `QvantumCloudClient` and `QvantumModbusClient`.

### Add QvantumModbusClient and delegate Modbus I/O from QvantumAPI ([#209](https://github.com/perosb/qvantum_custom_component/pull/209))

Adds `QvantumModbusClient` in `client/modbus/client.py` with metrics/settings reads, identity probe, holding writes, and high-level setters. `QvantumAPI` constructs the client when `modbus_tcp=True` and delegates register I/O through it. Extra-DHW restore timer stays on `QvantumAPI`. Compatibility properties (`_modbus_device`, `_modbus_lock`, `_modbus_write`) keep existing tests working. Direct client tests in `tests/test_modbus_client.py`. Depends on #208.

### Add QvantumCloudClient and delegate HTTP I/O from QvantumAPI ([#210](https://github.com/perosb/qvantum_custom_component/pull/210))

Adds `QvantumCloudClient` under `client/cloud/` (endpoints, Firebase auth, REST). Owned HTTP sessions use `aiohttp.ClientTimeout(total=20, connect=10)`. `QvantumAPI` constructs the cloud client in HTTP mode, forwards token/session attributes used by tests, and delegates authenticate, metrics, settings, commands, and elevate-access. Extra-DHW timer policy remains on `QvantumAPI`. Depends on #209.

### Cut over HA to Cloud XOR Modbus clients and drop QvantumAPI ([#213](https://github.com/perosb/qvantum_custom_component/pull/213))

Setup constructs `QvantumCloudClient` **or** `QvantumModbusClient` (never both). `QvantumAPI` is gone from production. `ExtraDhwTimer` is created only in Modbus mode; extra DHW duration stays in HA, not in the client. Coordinators, entities, services, and config flow use `runtime_data.client` / `coordinator.client`. Tests keep a thin `QvantumAPI` helper plus a Modbus adapter so existing facade coverage still runs. pytest now fails after 30s (`pytest-timeout`) so a stuck lock test cannot hang the suite. Stacked on the merged client extraction (#207–#211).

### Mark status entities as EntityCategory.DIAGNOSTIC ([#222](https://github.com/perosb/qvantum_custom_component/pull/222))

Put status/diagnostic entities under **Diagnostics** in the HA UI (brainstorm item “Diagnostik-kategori”, not a GitHub issue).

### Add water_heater platform for DHW/VV ([#223](https://github.com/perosb/qvantum_custom_component/pull/223))

Adds a Home Assistant `water_heater` entity wrapping existing DHW/VV APIs (no new Modbus registers). `current_temperature` prefers `bt30`, then `bt31`/`bt34`; `target_temperature` is `tap_water_stop` (written via `set_tap_water`). Operation modes: Eco/Normal/Extra/Smart from `dhw_mode` / `extra_tap_water`; Off via `op_man_dhw`. Extra uses `async_set_extra_tap_water` (indefinite, same as the existing switch). Eco/Smart writes require Modbus holding 53. Keeps existing number/switch/button VV entities; fixes outdated HTTP-only comment for `tap_water_capacity_target`. Unit tests for mode mapping and cloud vs Modbus setup; en/sv translations; README Features line.

### Add device triggers and conditions for status bits ([#225](https://github.com/perosb/qvantum_custom_component/pull/225))

Adds Home Assistant device triggers and conditions for heat-pump status entities (defrost, compressor blocked, freeze protection, Wi-Fi/cloud disconnect, ventilation filter soon due). Filter-soon-due uses a fixed **48 hour** threshold (`FILTER_SOON_DUE_HOURS`). Includes `en`/`sv` device_automation labels, README section, and unit tests for schema/attach/helpers.

### Add Modbus compressor and fan runtime sensors ([#226](https://github.com/perosb/qvantum_custom_component/pull/226))

Map Modbus input registers 88–90 (`compressor_run_time`, `compressor_starts`, `ventilation_fan_run_time`) from QAD EN 2609-AXC. Expose them as diagnostic sensors in local Modbus mode: hours as `DURATION` + `TOTAL_INCREASING`, starts as a count. Filter remaining life is unchanged. Add translations in all locales.

### Add Modbus user-defined heating curve ([#228](https://github.com/perosb/qvantum_custom_component/pull/228))

Expose Modbus heating curve holdings 22–30 in Modbus mode (writes opt-in). `curve_type_heating` is a select (0=Auto, 1=User defined) with a `points: [[outdoor, supply], …]` attribute for ApexCharts/Plotly. Auto curve number is `temp_compensation_curve` (1–50). User-defined supply points are named after outdoor temperature (`curve_-30` … `curve_30`, 10–80 °C). Curve temperature numbers are only available when curve type is User defined.

### Expose heating curve over cloud HTTP settings ([#230](https://github.com/perosb/qvantum_custom_component/pull/230))

Create the Auto/User defined heating-curve select and `ud_curve*` point numbers in **cloud HTTP** mode (same entities as Modbus). Writes send only `curve_type_heating` and `ud_curve*` as in the official app. DUT / `guide_sdot` / `guide_tdot` are not sent yet. Poll aliases `ud_curve_minus30` → canonical `curve_minus_30` so one set of entities works on both transports.

## Bug fixes

### Handle HTTP 503 and 5xx server errors gracefully ([#220](https://github.com/perosb/qvantum_custom_component/pull/220))

When Qvantum's cloud API responds with HTTP 503 Service Unavailable (or other 5xx errors like 502/504), the cloud client previously fell through to the default `case _:` branch in `get_settings()`, which logged an error and silently wiped cached settings (`self._settings_data = {}`). In `_get_http_values()`, 503 returned `(None, None, None)`, causing `get_metrics()` to treat it as a 304-style cache hit. Consequently, the coordinator did not detect an API failure, entities lost their settings-derived values and broke individually, rather than cleanly transitioning to `unavailable`. This PR: 1. Treats all HTTP status codes `>= 500` as `TransportError` in `get_device_metadata`, `_get_http_values`, and `get_settings`. 2. Preserves existing cached settings and metadata during transient server outages instead of wiping them. 3. Explicitly catches `APIConnectionError` (`TransportError`) in `QvantumDataUpdateCoordinator.async_update_data()`, raising `UpdateFailed` so Home Assistant correctly marks the coordinator update as failed and sets entities unavailable without traceback spam. 4. Adds test cases covering 500 and 503 responses for `get_settings`, `get_device_metadata`, and `get_metrics`, verifying cache preservation and clean `UpdateFailed` propagation.
