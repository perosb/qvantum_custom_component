# 2026.9.11

_Released 2026-09-10 · [compare 2026.9.3…2026.9.11](https://github.com/perosb/qvantum_custom_component/compare/2026.9.3...2026.9.11) · [all releases](https://github.com/perosb/qvantum_custom_component/tree/main/docs/releases)_

You can now adjust the outdoor-temperature limit for stopping heating in either setup, and see more pump status, connection, vacation, and relay indicators. Temperature settings now show Celsius, and climate control works with an external room sensor, shows its reading, and allows adjustments in 0.1° steps; controls also appear only in setups that support them. The update also fixes extra-hot-water timer behavior and improves how settings and device information are handled.

> [!IMPORTANT]
> Setup is **Cloud HTTP** or **local Modbus**.
> Local Modbus is read-only until writing is enabled.
> SmartControl stay cloud-only.


> [!WARNING]
> **Modbus mode**
> Enabling Modbus writing means you accept full responsibility for values written to the pump.
> Incorrect or out-of-range values may void the warranty and/or affect lifecycle and performance.


> [!WARNING]
> **Cloud mode**
> Elevate access assigns "Remote Service" (service tech) rights to your user. Cloud HTTP only.
> Cloud mode uses the same internal API as the app. Use at your own risk ;)

## New features

### Add outdoor temperature stop heating number entity for Modbus ([#186](https://github.com/perosb/qvantum_custom_component/pull/186))

Adds a writable Home Assistant **number** entity for **Outdoor temperature stop heating** in Modbus mode. The register was already in `MODBUS_HOLDING_REGISTER_MAP` but not exposed as an entity. This wires it through the same Modbus-only number path as `dhw_stop_extra`: Read via holding settings (`MODBUS_HOLDING_TO_SETTINGS_MAP`). Write via `write_holding_register_for_metric` when **Enable writing via Modbus** is on. Unavailable when Modbus writing is off (no HTTP endpoint for this setting).

### Add cloud support for outdoor temperature stop heating ([#189](https://github.com/perosb/qvantum_custom_component/pull/189))

Expose **Outdoor temperature stop heating** in Cloud/HTTP mode using the API setting name `stop_heating`. The number entity is now keyed by `stop_heating` in both modes: **Cloud:** read from HTTP settings, write via `update_setting(..., "stop_heating", value)`. **Modbus:** holding register 18 (`outdoor_stop_heating`) is aliased to `stop_heating`; `update_setting` still writes the holding register when Modbus writing is enabled No config-entry / unique-id migration.

### Add Modbus status, connectivity, and vacation input registers ([#196](https://github.com/perosb/qvantum_custom_component/pull/196))

Map remaining readable Modbus **input** registers from QAD EN 2609-AXC: Extend the input poll from 161–164 to 161–170; still skip the refused 105–160 hole. Released flags become binary sensors. Translations now mean **permitted** (EN *permitted*, SV *tillåten*, DE *freigegeben*), not “liberated”. Wi-Fi and cloud connected are **diagnostic** connectivity binary sensors. Vacation mode stays a writable switch on HTTP; on Modbus it is a read-only binary sensor (input 170).

- **#1 (0–104):** `unit_state` (40), `heating/cooling/compressor/additionreleased` (42–45), `compressor_blocked` / `_sec` (71–72), `freeze_protection_active` (87), `ventilation_filter_time_left` (91)
- **#3 (168–170):** `wifi_connected`, `cloud_connected`, `vacation_mode` (price registers 165–166 skipped)

### Expose remaining picpin relay bits as binary sensors ([#203](https://github.com/perosb/qvantum_custom_component/pull/203))

Create binary sensors for the remaining `picpin_relay_*` bits (`gp10`, `qn8_1`, `qn8_2`, `gp3`, `ha12`) and Modbus-only `picpin_relay_pump`. These were default-enabled metrics that never became entities (`picpin_` is excluded from numeric sensors, and they were missing from `BINARY_SENSOR_NAMES`), so HTTP/Cloud logged `Adding new default metric ... since it's not in the registry` on every poll. Skip that debug log for default metrics that cannot land in the entity registry (switch/select-style excluded patterns).

## Bug fixes

### Add °C unit and temperature device class for outdoor_stop_heating ([#187](https://github.com/perosb/qvantum_custom_component/pull/187))

Addresses the Code Reviewer optional nit from #186: set `°C` (`UnitOfTemperature.CELSIUS`) and `NumberDeviceClass.TEMPERATURE` on the `outdoor_stop_heating` number entity. Updates `test_init_outdoor_stop_heating` to assert unit and device class. Minimal change scoped only to `outdoor_stop_heating`.

### Extend °C unit and temperature device class to remaining temperature number entities ([#188](https://github.com/perosb/qvantum_custom_component/pull/188))

Follow-up to #187: extend `UnitOfTemperature.CELSIUS` and `NumberDeviceClass.TEMPERATURE` from `outdoor_stop_heating` to the remaining temperature number entities via a shared `TEMPERATURE_NUMBER_METRICS` frozenset. Covered metrics: `outdoor_stop_heating`, `indoor_temperature_offset`, `tap_water_start`, `tap_water_stop`, `dhw_stop_extra`, `room_temp_external`. Tests assert unit + device class for the five newly covered metrics (`outdoor_stop_heating` already covered in #187).

### Omit SmartControl entities in Modbus mode ([#191](https://github.com/perosb/qvantum_custom_component/pull/191))

Do not create the three SmartControl entities in local Modbus mode: `use_adaptive`, `enable_sc_sh`, and `enable_sc_dhw`. They stay in cloud HTTP mode. Switching to Modbus drops leftover SmartControl entities from the registry.

### Cancel extra-DHW restore timer when Extra is stopped ([#192](https://github.com/perosb/qvantum_custom_component/pull/192))

fix: Cancel extra-DHW restore timer when Extra is stopped.

### Stop requesting tap_water_start/stop as HTTP metrics ([#197](https://github.com/perosb/qvantum_custom_component/pull/197))

`tap_water_start` and `tap_water_stop` are settings (HTTP settings API / Modbus holding registers), not `/values` metrics. They were listed in `REQUIRED_METRICS`, so HTTP mode asked the values endpoint for them on every poll and logged `Metric tap_water_start not found in response data.` (same for `_stop`). Number entities still get the values from the settings response; they are just no longer requested as HTTP metrics. Fixes #195.

### Stop using deprecated device_registry.devices mapping ([#200](https://github.com/perosb/qvantum_custom_component/pull/200))

Home Assistant 2026.8 warns when a custom integration treats `device_registry.devices` as a mapping (`devices.values()`, `.get()`, etc.). That mapping surface is removed in 2027.9. This replaces those lookups with the supported helpers: `DeviceRegistry.async_get_device_by_identifier()` for a known Qvantum identifier, scoped to the config entry. `device_registry.async_entries_for_config_entry()` when recovering device identity after a restart. `entity_registry.async_entries_for_device()` (including disabled entities) when enumerating entities for that device Call sites: `cleanup_disabled_entities`, `_get_enabled_metrics`, `_device_from_registry`, and firmware version updates on the maintenance coordinator.

### Request stop_heating in REQUIRED_METRICS for HTTP cloud mode ([#201](https://github.com/perosb/qvantum_custom_component/pull/201))

fix: Request stop_heating in REQUIRED_METRICS for HTTP cloud mode.

### Harden device-registry helpers after #200 ([#202](https://github.com/perosb/qvantum_custom_component/pull/202))

Unify config-entry id access: `_get_enabled_metrics` and `_device_from_registry` now use `_coordinator_config_entry_id` (same as cleanup). Maintenance firmware updates call shared `async_get_qvantum_device_entry` instead of duplicating identifier lookup. Restore/strengthen tests that a device belonging to another config entry is ignored (identifier helper + cleanup + `_device_from_registry`). Bonus: v5 sensor migration uses `er.async_entries_for_config_entry` instead of `ent_reg.entities.values()`. Follow-up to #200. Missing `entry_id` still returns `None` intentionally (stricter than the old all-devices scan).

### Allow climate target temperature with external room sensor ([#204](https://github.com/perosb/qvantum_custom_component/pull/204))

Climate previously only offered `TARGET_TEMPERATURE` when `sensor_mode` was BT2 (`"bt2"` / `1`). Indoor setpoint is now also available when using an external room sensor: HTTP `ext_room_sensor` or Modbus `SensorMode.EXTERNAL` (4). Adds `SensorMode` IntEnum for Modbus holding 9 (`use_operation_sensor`) and uses it in climate, `room_temp_external`, and the indoor sensor source select.

### Use 0.1°C steps for climate target temperature ([#205](https://github.com/perosb/qvantum_custom_component/pull/205))

Climate UI used whole-degree steps because `target_temperature_step` was unset. Set `_attr_target_temperature_step` to `PRECISION_TENTHS` (0.1°C) so the indoor setpoint matches the pump's 0.1°C resolution.

### Show climate current temperature from the selected sensor ([#206](https://github.com/perosb/qvantum_custom_component/pull/206))

Climate \`current_temperature\` always came from BT2, so an external room sensor never showed on the climate card. BT2 mode still reads \`bt2\`. External mode (\`ext_room_sensor\` / \`SensorMode.EXTERNAL\`) reads \`room_temp_external\` (Modbus) or \`room_temp_ext\` (HTTP). Availability follows the selected sensor, so climate stays available with an external reading even if BT2 is missing. \`room_temp_ext\` is now a required HTTP metric so the external reading is fetched even when that sensor entity is disabled.
