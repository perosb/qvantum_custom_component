## New features

### Add self-calibrating solar-gain core ([#282](https://github.com/perosb/qvantum_custom_component/pull/282))

Ports the identification half of the standalone `docs/solar_heat_forecast.py` into `custom_components/qvantum/solar_gain.py`: no Home Assistant imports, no pump writes, no behavior change yet. Two-stage weighted fit (opaque hours → `a`/`c`, solar residual → `b`) with exponential recency weights (half-life 30 days) and one robust studentised-residual pass per stage, so one bad hour cannot swing the fit and the model follows the current season. Replaces the binary `FitTrust` / soft-level policy with a continuous `trust` in [0, 1] from `b`'s t-stat (`t²/(t²+2²)`). Weak evidence contributes almost nothing to the solar offset without manual calibration. Residual R² is kept as a diagnostic only — in-sample R² is upward-biased for small samples and would overstate trust. Effective-GHI kernel: exponential decay over past and forecast hours, so a single cloud or spike moves the solar term by a fraction of an hour.

### Add Open-Meteo forecast and GHI history client ([#283](https://github.com/perosb/qvantum_custom_component/pull/283))

Adds `custom_components/qvantum/open_meteo.py`: forecast (hourly outdoor temperature + GHI around now, past hours for the smoothing kernel, future hours for the outdoor term) and historical GHI with the archive API as fallback. No API key. The caller passes the HA `aiohttp` session, so the module stays Home Assistant-import free and never owns or closes a session. Transport and payload failures raise `OpenMeteoError`; callers treat a missing forecast/history as "no solar term / not ready", never as a reason to write to the pump.

### Add pure heating-curve computation ([#285](https://github.com/perosb/qvantum_custom_component/pull/285))

Adds `custom_components/qvantum/heating_curve.py`: baseline + **one** shared adjustment in °C over four forecast-driven terms — outdoor trend anticipation (forecast series, not instantaneous BT1), bounded daylight-rhythm offset, uncertainty-weighted solar gain converted to supply degrees through the local baseline slope, and a one-sided load reduction when the pump coasts below model demand (expected demand includes the solar term, so solar is not double-counted). Indoor deviation is a **cap only**: warm margin vetoes upward adjustment, cold margin vetoes downward adjustment, it never drives a term. Points are clamped to 10–80 °C and enforced non-decreasing toward colder outdoors (falling toward warmer). `integer_points()` gives whole degrees for Modbus writes. Pure module: no Home Assistant imports, no pump writes.

### Add shadow custom-curve coordinator and sensors ([#286](https://github.com/perosb/qvantum_custom_component/pull/286))

`curve_coordinator.py`: Modbus-only `DataUpdateCoordinator` (15 min). Freezes the Auto baseline once, calibrates the solar model from long-term recorder statistics + Open-Meteo history (refresh 24 h), computes the shadow curve from forecast/solar/night-day/load, and compares the interpolated supply against `cal_heat_temp`. A missing forecast/history only sets a `blocker`; the update never fails. `ready` follows the plan: three full local days of `custom_curve_deviation` statistics, coverage ≥ 90 %, median |deviation| ≤ 1.0 °C, max ≤ 3.0 °C. New sensor family (`custom_curve_30` … `custom_curve_minus_30`, `custom_curve_adjustment`, `custom_curve_deviation`, `custom_curve_solar_model`) with stable English slugs via explicit `suggested_object_id`; translated names in all 11 locales. Replaces `heating_curve_advisor`: the indoor-deviation window is now the curve module's cap input instead of an advice state. No pump writes in this layer.

### Add active custom-curve control ([#287](https://github.com/perosb/qvantum_custom_component/pull/287))

Manual activation only: new switch `switch.qvantum_custom_curve_control` (stable slug, translated in all 11 locales) and service `qvantum.set_curve_control` with `mode: shadow|active`. Activation sequence exactly as planned: write holding 24–30 while 22 is still Auto (firmware ignores the table), zero the parallel offset (holding 15), read back and verify every point, and only then set 22 to User defined. If the pump was already User defined, it is first returned to Auto during the point writes. Active cycles rewrite changed points only (≥ 1 °C diff), one point at a time with a 1 s pause, and optimistically update the main coordinator via `handle_setting_update_response` so entities and diffing stay consistent between polls. Safety reversion: any failed/not-applied write, invalid table (outside 10–80 or not falling), lost connection, or pump moved off User defined writes holding 22 back to Auto and returns to shadow. A revert that cannot be written (connection gone) is latched and retried on later cycles. Modbus-only and gated on the Modbus write option; the switch is the only user-facing source of truth.

### Make the active curve self-correct from pump limits and indoor error ([#291](https://github.com/perosb/qvantum_custom_component/pull/291))

Implements the next plan steps: pump-own supply limits, automatic per-point trims, and transparency. Modbus-only; no cloud path and no new entities. **Pump supply limits (step 1).** Holding 19/20 are now read (added to the Modbus settings map) and used as the effective clamp for computed points and the write gate, instead of the register range 10–80 °C. A point is never written above what the firmware will actually use, and clamping is exposed (`clamped`) and logged when the state changes. **Automatic per-point trims (step 2).** While the curve is active, hourly `(BT1, indoor − target)` from recorder statistics is bucketed by outdoor temperature, converted to supply degrees through the local curve slope, and folded into a per-point trim with a damped step. Evidence-gated (≥ 6 hours per bucket, nothing farther than 7.5 °C from a reference point), capped at ±2 °C, updated at most daily, cleared on reversion or baseline re-learn. It only runs while active — in shadow the baseline learning owns the shape — and pauses when the indoor cap or the shared-adjustment clamp is active, so it never fights the existing safety bounds. **Transparency (step 3).** Point sensors expose `trim`; the adjustment sensor exposes `trims` and `clamped`; the deviation sensor exposes the baseline fit's `baseline_learned_hours`, `baseline_outdoor_min_c`, `baseline_outdoor_max_c`. **Docs (step 4).** `docs/heating-curve.md` gains an "Active trims" section, the pump-limit behavior, and a "Seasonality" section. No user action is required after the switch is on; the winter correction is automatic.

### feed external room temperature to holding 14 from an HA sensor ([#299](https://github.com/perosb/qvantum_custom_component/pull/299))

**Why:** the Qvantum app's "ext modbus" sensor mode expects a fresh room temperature on holding 14 at least every ~5 min; when it goes stale the pump drops the sensor source and raises **alarm 8** ("Controlling room temperature sensor(s) unavailable"). The documented workaround — a state-triggered automation writing the number entity — stops writing whenever the source temperature is stable, so a quiet afternoon trips the watchdog (verified in the field: 4 writes in 12 h, then 4 h without writes → source dropped → alarm 8). **Modbus-only options picker** ("External room temperature source", entity selector filtered to temperature sensors). When set, the coordinator writes an EMA-smoothed value (τ = 5 min) to holding 14 on its own timer — never slower than every 4 minutes, regardless of the configured poll interval — clamped to the datasheet range (−5…40 °C). Writes happen even when the value is unchanged and regardless of the pump's current sensor mode, so the app can be switched to "Ext Modbus"/"Alla" at any time. No writes in cloud mode or while Modbus writing is off. **Room_temp_external number availability** no longer requires the pump's sensor mode to be 4. The old gate locked the entity out exactly when the pump dropped the source, making recovery impossible; write access is the only gate now. Manual writes still work and are overwritten by the next feed poll. **Diagnostics:** new `external_room_feed` section (configured entity, last value, last write timestamp, write-error count). **Docs/translations:** README section on the watchdog, the app's sensor modes, and the fixed-interval requirement for legacy manual automations; option strings in all 11 translation files. Also includes `chore: ignore .ha-token` (protects a local HA token from ever being committed).

## Bug fixes

### Honor coordinator availability and enforce entity write guards ([#274](https://github.com/perosb/qvantum_custom_component/pull/274))

Adds `QvantumAccessMixin._coordinator_available` (the coordinator's `last_update_success`) and the base `QvantumEntity.available`. Every platform `available` override now ANDs its data check with it, so a failed poll no longer leaves stale values reported as available. Adds `QvantumAccessMixin._require_write_access()` and calls it first in every write path: `climate.async_set_temperature`, `water_heater.async_set_temperature` / `async_set_operation_mode`, `fan.set_fanspeedselector`, `switch.async_turn_on/off`, `number.async_set_native_value`, `select.async_select_option`. Home Assistant services bypass availability, so this closes the read-only write gap (H2). Readability no longer depends on write access for `climate`, `water_heater` and `fan`: a read-only account still sees temperatures/fan state, while writes are refused (H18 decision). `vacation_mode` keeps its intentional no-elevation write path (guard is skipped for that metric), matching its existing availability. `AGENTS.md` documents the availability/write-guard conventions. Cloud vs Modbus: no transport-specific behavior change; the guard uses the existing `_has_write_access`, which already encodes cloud `writeAccessLevel` and Modbus `CONF_MODBUS_WRITE`. Fixes H1, H2 and the H18 readability decision from the plan (steg 7).

### Harden coordinator poll and restore paths ([#275](https://github.com/perosb/qvantum_custom_component/pull/275))

**H3 poll**: `async_update_data` now creates explicit tasks for metrics/settings and cancels the sibling when one fails (previously `asyncio.gather` left an orphaned request running past the poll). **G15/H6 store validation**: `async_restore_dhw_state` coerces Store values to finite numbers, dropping non-numeric values and requiring positive shower duration/flow. A corrupted Store file (e.g. `shower_duration: 0`) used to raise `ZeroDivisionError` on every poll. `ExtraDhwTimer.async_restore` now rejects bool and implausible (far-future / negative) deadlines and clears them. **H5 restore**: a failed DHW→Normal write keeps the deadline and reschedules a retry instead of leaving `restore_at` armed with no callback. **G7 cloud client**: new `_decode_json` maps non-JSON bodies on successful responses to `TransportError`, used across auth, metrics, settings, metadata, devices, access-level and command paths. **G16**: `fan0_10v` keeps its raw value when it cannot be scaled instead of failing the whole poll. **H4**: the access-expiry sensor handles `access_level: None` without `AttributeError`. Cloud vs Modbus: the JSON/timer/Store hardening applies to both transports; no user-visible behavior change for well-formed data. Fixes H3, H4, H5, H6, G7, G15, G16 from the plan (steg 8).

### Validate Modbus writes, make tap-water writes atomic, and add timeouts ([#276](https://github.com/perosb/qvantum_custom_component/pull/276))

**G1 validation**: holding-register fields now carry a signedness validator (`client/modbus/model.py`). `encode_int` only checks the 16-bit width, so a negative value written to an unsigned register used to silently wrap to a large positive one. Domain min/max and read-back verification are deliberately left for a follow-up: the maps are the datasheet, and per-register ranges/read-back need datasheet-verified values and an extra round trip per write. **G2 atomicity**: `set_tap_water` writes start/stop under a single lock acquisition so a concurrent poll cannot observe a half-applied pair, and orders the writes so `start < stop` holds at every intermediate step. Inverted pairs and single values crossing the current counterpart raise `ValueError`. **G3 timeout**: `_run` bounds every operation with `asyncio.wait_for` (default 15 s, injectable via `operation_timeout`) and maps a timeout to `TransportError` instead of holding the client lock forever. **G4 lifecycle**: `attach_unit()` clears the closed flag so a client can be reused after `close()`. Client is HA-free; `_decode_json`-style isolation untouched. `AGENTS.md` notes the timeout and signedness validation. Fixes G1–G4 from the plan (steg 9).

### Harden cloud request handling ([#277](https://github.com/perosb/qvantum_custom_component/pull/277))

Covers all of steg 10 (G6, G8–G11): cloud request robustness in one concern. **G6 Retry-After**: `RateLimitError` carries `retry_after` (parsed from the `Retry-After` header as seconds or HTTP-date). The coordinator temporarily widens its poll interval while throttled (capped at 1 h) and restores the configured interval on the next successful poll. **G8 URL encoding**: device ids, access codes and metric names are URL-encoded (`quote` / `urlencode`) before being interpolated into cloud request URLs. **G9 diagnostics**: `TransportError` includes a truncated response body and the `x-request-id` header; the full response body is no longer logged on every debug line (`_preview`). **G11 monotonic expiry**: token expiry is a `time.monotonic()` deadline, so a wall-clock jump cannot discard a fresh token or honour a stale one; extra-DHW/fan `stopTime` is computed from a timezone-aware UTC now. **G10 elevate-access**: `_has_sufficient_access()` documents the expiresAt logic and parses naive/malformed timestamps leniently without raising; `get_access_level()` is reused instead of duplicating the access-level GET. `client/` stays Home-Assistant-free. Fixes G6, G8, G9, G10, G11 (steg 10).

### Hide write controls without write access ([#278](https://github.com/perosb/qvantum_custom_component/pull/278))

After the availability/write-guard split, climate/water_heater/fan stayed readable without write access, but they still advertised their write features. In Modbus mode with **"Allow writing via Modbus" off**, the UI therefore showed an indoor setpoint, DHW target/operation mode, and fan speed control — each of which only failed on use with `Write access is not enabled for this entity`. Gate `supported_features` on `_has_write_access`: The entities remain **available** and keep reporting current temperature / state; only the controls disappear. Control entities (switch, number, select, button) already gate availability on write access and are unchanged. `AGENTS.md` updated to the refined rule. Fixes the reported Modbus no-write UI gap (H18 follow-up).

- `climate`: no `TARGET_TEMPERATURE` without write access.
- `water_heater`: no `TARGET_TEMPERATURE`/`OPERATION_MODE`/`ON_OFF` without write access.
- `fan`: no `PRESET_MODE`/`TURN_ON`/`TURN_OFF` without write access.

Implements steg 11 (H10, H11, H12, H17, H19). H18 was already landed in #274/#278. **H10 water_heater**: the cloud API has no `dhw_mode` setter, so Eco/Smart are **Modbus-only**. `operation_modes_for_values` now keys solely on `modbus_enabled` (cloud always shows Normal/Extra/Off, even if `dhw_mode` leaks into the payload). ### Number custom-curve points so they sort like the pump ([#289](https://github.com/perosb/qvantum_custom_component/pull/289))

The seven custom-curve point sensors were named/slugged `custom_curve_30` … `custom_curve_minus_30`, so an entity list sorted them alphabetically as `-10, -20, -30, +10, +20, +30, 0` instead of the pump's curve order. Give each point a numeric index in both the friendly name (`Egen värmekurva 1: 30°C` … `7: -30°C`, translated in all 11 locales) and the entity id (`custom_curve_01_30` … `custom_curve_07_minus_30`) — the same pattern the pump's own `curve_01_30` … `curve_07_minus_30` numbers use, so the two sets sort together (+30 … −30). Unique ids and translation keys are unchanged; the integration is unreleased, so the entity ids can be renamed. Docs updated to the new point entity ids.

### Write fractional room compensation factors ([#296](https://github.com/perosb/qvantum_custom_component/pull/296))

`QvantumNumberEntity` coerced `room_comp_factor` with `int(value)`, so 0.5 was written as 0 and 1.5 as 1. In Modbus mode raw 0 on holding 13 is rejected by the pump with `Modbus Exception 0x03` (datasheet minimum is 0.5 → raw 5), which made only 1 and 2 writable. The value now passes through as a float; cloud writes send the exact value too. In Modbus mode the entity exposes holding 13's documented range 0.5–2.0 (QAD EN 2609-AXC, scale 10) instead of the cloud range 0–10, so the UI cannot offer values the register rejects. Cloud keeps 0–10. Regression tests: entity write passes 0.5 through, Modbus device encodes 0.5 → raw 5, and setup picks the Modbus-specific bounds.

### Clamp Modbus number ranges to the datasheet ([#297](https://github.com/perosb/qvantum_custom_component/pull/297))

`room_temp_external` exposed 10–40 but Modbus holding 14 is −5–40 (QAD EN 2609-AXC), and writing below 10 was impossible. The metric is Modbus-write-only, so the range is now −5–40 everywhere. `indoor_temperature_offset` exposed ±10 but holding 15 is −9–9. Modbus now uses ±9; cloud keeps ±10, the same split as the earlier `room_comp_factor` fix. Writing outside a holding's documented range returns Modbus exception 0x03, which these bounds prevent.

### reject DHW Eco/Smart writes after QSG EN 2613-A ([#300](https://github.com/perosb/qvantum_custom_component/pull/300))

QSG EN 2613-A narrows Modbus holding 53 (DHW Mode) to `1=Normal, 2=Extra`; the pump rejects the older `0=Eco / 3=Smart` values with Modbus exception 0x03. This aligns the integration with the new datasheet. `MODBUS_HOLDING_RANGE["dhw_mode"]` is now `(1, 2)`, so the client rejects 0/3 before the wire instead of letting the pump fault. Water heater no longer **offers or writes** Eco/Smart on either transport (they were Modbus-only before). Both transports now expose the same `Normal/Extra/Off` list. Reading stays defensive: `map_operation_mode` still maps 0/3 for a unit that reports them; the constants and translations remain. Datasheet references updated from QAD EN 2609-AXC to QSG EN 2613-A. Not in this PR (needs vendor confirmation): input 33 relay bit map. QSG EN 2613-A says bit 7 = "Pump 1 & 2", bit 8 = HA12, with no GP3 bit, while the code follows live dumps (`gp3=7, pump=8, ha12=9`).
